# Dayloopで約束を追跡するための会話プロンプト

以下をDayloopのMCPツールを使える会話に貼り付けてください。初回の検証は、専用の `DAYLOOP_HOME` を設定したサンプル台帳で行います。

```text
Dayloopを使って、依頼から最終的な決着まで追跡してください。
対象は私が相手に依頼した仕事と、その返答を待つ仕事です。

会話の最初に get_today と commitment_list を読み、登録済みの約束を確認してください。
確認日時が未来の約束を、毎日の持ち越しや同じ確認の対象にしないでください。
必要な確認は plan_day / check_in の questions を使い、1問ずつ聞いてください。
計画確定の前に約束・変更提案への回答を処理し、plan_dayを再表示してください。
私が最後の確定質問に明示回答したら、そのdateとplan_revisionでconfirm_planを呼んでください。
版が変わった、期限が到来した、または未回答が残った場合は、再表示して確認し直してください。

新しい約束は、依頼内容、待ち相手、返答期限、次の確認日時、
関連タスクと「この返答が来るまで進められないか」、出所、根拠を確認し、
commitment_register で登録してください。日時はタイムゾーン付きで扱ってください。
返答を受けたことと、仕事全体の完了は別です。

追加情報、期限変更、取消、返答は commitment_ingest に提案として記録してください。
件名だけで結び付けず、出所の識別子と約束IDを確認してください。
対応先が不明な場合は候補のID・相手・根拠を示して私に選ばせてください。
情報の取得失敗や部分取得は commitment_sync に記録し、
「返答なし」「変更なし」と断定しないでください。

重要な変更の前には commitment_history で変更前後と根拠を読み、
私が内容を明示的に選択・承認してから commitment_apply を呼んでください。
私の回答がない限り confirmed=true を生成しないでください。
質問後にrevisionが変わった場合は再取得し、変更内容を示して確認し直してください。
operation IDと外部イベントIDは同じ操作の再試行で維持し、別の操作では新しくしてください。

確認時は commitment_check を使います。
まだ待つ場合は次の確認日時と根拠を残してください。
返答を確認した場合は内容と次の自分の作業を確認し、必要なら add_task で作業を作って関連付けてください。
返答だけで finish_task を呼ばないでください。
最終的な決着は、私が根拠を明示して決着を承認してから確定してください。
日を閉じるときは既存の日次確認の回答を処理し、close_day の結果を確認してください。
closedは既に閉じた事実、pending_countとquestionsは現在の未回答として別々に確認してください。
closed=trueでも質問が残る場合は、日を再開せず、閉じた後の確認として私に聞いてください。

本文を外部AIへ送ること、Outlook/Teamsの実データを読むこと、Jira連携、
外部への送信、コミット、push、公開はこのプロンプトでは許可しません。
分類や照合にAIを使えなくても、ID選択と手入力で進めてください。

次の安全なサンプルを順に試してください。
1. 「設計レビュー」をサンプル担当Aへ依頼。水曜に返答予定。
2. 火曜のサンプル通知で返答期限が木曜へ変更。元の約束に結び付け、私の承認後に反映。
3. 水曜は確認不要。木曜の確認日時には根拠と一緒に提示。
4. サンプル返答を取り込み、私が内容を確認。次の作業「レビュー指摘を反映」を追加。
5. 反映と合意が終わった根拠を私が提示し、約束を決着。
途中で日を閉じ、再起動しても約束ID・次の確認日時・履歴が残ることを確認。
同じ通知の再取込、同じ件名の別依頼、古い変更、取消、取得失敗も試し、
成功・拒否・未確認を区別して台帳のIDと状態を報告してください。
```

CLIでは同じ処理を `dayloop commitment <register|list|ingest|apply|check|history|sync> --json '<JSON>'` または `--file <JSONファイル>` から呼び出せます。JSONの必須項目と現在の状態は、ツールの入力定義と台帳の返り値を確認してください。省略や無回答を承認として扱わないことが前提です。
