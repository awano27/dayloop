# 段階3の穴

Jev を足す前に、台帳と質問の形を一段揃える。判断モデルは合法な選択肢の中から選ぶので、選択肢の一覧と日付・件数の計算がコード側でずれていると、そのずれごと採用される。

## 不変条件5が MCP では閉じていない

CLI の `plan_ritual` は、前日の open が残っていると今日の確定質問へ進まない。

MCP の `plan_view` は、未クローズ日の質問の後ろに、今日の `confirm_plan` を常に付ける。`confirm_plan` ツールは未クローズ日を見ずに `plan_confirmed_at` を書く。

朝の計画が「前日の確定から始まる」は、対話 CLI の順序であり、台帳の拒否ではない。MCP クライアント（Copilot 含む）は今日を確定したまま前日を開けておける。

段階3.1で `confirm_plan` を、前日に open が残るあいだは拒否する。質問列からも、そのあいだは確定の選択肢を出さない。

## 質問文が二系統ある

`engine::Question` と `rituals` の `ui.choose` が、同じ場面の文言を別々に持っている。MCP ツール説明の一部は、廃止した `resolve_with` のまま残っている（`docs/decisions.md` は `options[].tool` に更新済み）。

例: `plan_day` / `check_in` / `close_day` の description が「resolve_with のツールで反映」と書いている（`src/tools.rs`）。

クライアントは説明文を手順として使う。廃止したフィールド名が残ると、存在しない引数を組み立てる。質問カタログは `engine` の1か所にし、CLI はその `options` を表示する。

## 台帳が外に出していない列

`tasks.carried_from` は持ち越しと分割の親子を保存するが、`TASK_COLS` に無く、`Task` にも無い。候補の `task_id` も同様。振り返りで「同じ仕事の連鎖」を見る材料が DB の中だけにある。

スキーマは `CREATE TABLE IF NOT EXISTS` のみで版が無い。列追加が既存 DB に届かない。`schema_version` と、足りない列を足す移行を先に置く。

## コードがまだ計算していない事実

Jev の不得意（計算、計数、日付比較、長い無関係な state）にそのまま当たる処理が、まだ呼び出し側の純粋関数になっていない。

| 事実 | 現状 |
|---|---|
| 期限超過 | 表示時の文字列比較のみ。質問の入力にはならない |
| 見積と予定の空き | `estimate_min` は保存する。予定の分数との差し引きは無い |
| 営業日 | 土日だけ飛ばす。祝日は無い |
| 持ち越し回数 | 整数としては保存済み。質問 state に「回数」という文章で渡すと、モデル側の計数になる |

これらは Rust の関数が `overdue` / `fits` / `over` / `unknown` のような有限のラベルにしてから、判断モデルへ渡す。

## 取り込みはキーワードの先勝ち

`mail_hit` はフラグ、キーワード、重要送信者の順で最初の1件を候補にする。キーワードは「お願い」「please」などを含む。情報共有も候補になり、却下するまで残る（不変条件4）。

これはオフラインでも動く基準経路として残す。Jev は、この抽出結果に対する第二意見であり、COM の代わりにはしない。本文は既定で送らない（オブジェクトモデルガードと、抽出を判断モデルに任せない方針の両方）。

## 実行環境

- CI が無い。`cargo test` は手元だけ。
- テストは `DAYLOOP_HOME` のグローバル mutex で直列。
- `scripts/smoke.sh` は `target/release/dayloop.exe` を既定にする。
- トースト、COM、HKCU Run は Windows のみ。非 Windows では doctor が固有チェックを省略する。
- `serve` は pending でもその日のフェーズを実施済みにする。通知は1回で、同じ日に自動では聞き直さない。対話コマンドの再実行が回復手段。
- 分割は `carried_count` を 0 に戻す。分割した子を再び3回持ち越せる。意図的なら決定事項に残し、連鎖の上限が要るなら別のカウンタにする。
