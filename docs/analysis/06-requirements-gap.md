# 要件と実装の差分

要件を5つに割って、いま動くもの、意図的に別設計にしたもの、まだ無いものを分ける。

| 要件 | いま | 場所 |
| --- | --- | --- |
| 会議・開発・議事録・チケット・メールを入口にする | 半分。メールと予定だけ | `src/intake/` |
| 第一判断をいきなり Jev がやる | 違う。第一判断は過去の回答（枝）。Jev は未知の節のヒント1行 | `src/graph.rs`、`src/jev.rs` |
| 終われるものはどんどん終わりにする | 「処分」は自動、「完了」は自動にしていない | `src/store.rs` |
| 終われないものは次のタスクへ進む（順番・段取り） | 無い。並びは `created_at` 順 | — |
| 翌日は前日の積み残しから一から確認 | 出来ている。台帳が強制する | `src/store.rs`、`src/rituals.rs` |

---

## 1. 入口

動くのは Outlook デスクトップ（COM）のメールと予定である。メールはキーワード・フラグ・重要送信者の未読で候補になり、予定は24時間以内の会議が準備タスクの候補になる。ほかに手入力、`dayloop import` での Markdown 手編集、フィクスチャ JSON がある。

無いのは議事録とチケットである。`Candidate.source` は `teams` / `meeting` / `alert` という文字列を受け取れるが、そこへ書くアダプタが無い。議事録は「決定事項をタスクにする」工程なので、文章を読む生成の層と、候補か否かを閉じた集合で決める層に分かれる。チケットは状態を読めるので、次の3番と直接つながる。

## 2. 第一判断

いまの第一判断は Jev ではなく判断グラフである。件名、状況、送信者の順に枝を引き、枝があればその手で台帳を動かし、人には見せない。枝が無い節だけが質問になる。

Jev はその質問の手前に1行だけ札を貼る。しかも `close` の1箇所からしか呼ばず、`[jev] mode` は既定 `off` で、返答は画面のヒントであって台帳にもグラフにも書かない。枝が生えるのは人が `dayloop revise` したときだけである。

これは「Jev の返り値だけで枝を作らない」という決定に沿った形なので、要件が「Jev が第一判断をする」なら、ここは意図して開いている穴である。閉じる条件は `docs/jev-eval.md` の20件で帯を測ることで、帯より上を silent に台帳へ適用してよい、という順序になる。測る前に自動適用を入れると、誤った手が台帳に入る。

## 3. 「終わりにする」の中身

ここが要件のいちばん危ういところで、2つに割る必要がある。

**処分**（持ち越す、取り下げる、棚上げする、着手する）は自動にできる。すでに動いていて、同じ節の2回目からは質問が出ない。情報共有メールを棚上げする、不要な依頼を取り下げる、といった手は一度答えれば次から勝手に進む。

**完了**は自動にしていない。dayloop は「そのタスクが本当に終わったか」を観測できず、Jev も観測を持たない。件名から「完了した」は出てこない。いま `done` になる経路は、人が `dayloop done` と言ったか、Markdown の `[x]` を付けたか、枝が `done` を覚えている（=以前その件名を人が完了にした）かだけである。

自動で完了にしてよいのは、証跡を外から読めるときに限る。チケットが Closed になっている、PR がマージされている、会議が終わっている、といった観測を取り込めば、そこから `done` を silent に付けられる。証跡なしの自動完了は「忘れゼロを台帳で保証する」という前提を壊すので入れない。

## 4. 順番と段取り

未実装である。今日のタスクは `created_at` 順に並び、1件ずつ聞くだけで、優先順位も並び替えも「次はこれ」も無い。

材料は揃っている。`facts.rs` が期限との関係（`overdue` / `today` / `future`）と 09:00–18:00 の最大空きギャップに対する見積の当たり（`fits` / `over`）を出し、台帳は `due`、`estimate_min`、`carried_count`、予定表を持っている。足りないのは、それらを今日の並びに変える層である。

Jev の使いどころとしてはここが素直で、「A と B のどちらを先にやるか」の2択は閉じた集合で、計算は Rust 側が先に済ませられる。順番を決めるのは判断であって生成ではない。

## 5. 翌日の積み直し

出来ている。しかも儀式の順番ではなく台帳が強制している。

`plan` は前日の未クローズを先に閉じにかかり、open が残っているあいだ `confirm_plan` はエラーになり、計画の質問からも確定の設問が消える。持ち越しは次の営業日に新しいタスクを作り、`carried_from` で親子が辿れる。3回で止まり、分割・取り下げ・期限変更のどれかを要求する。既知の枝がある行は、翌朝もう一度聞かれることがない。

## 差を埋める順番

1. **順番の層**（`src/order.rs`）。期限、見積、空き、持ち越し回数から今日の並びを決める。Jev には「どちらを先か」の2択だけ渡す。ここが入ると「次のタスクを実行していく」が形になる。
2. **完了の証跡**。チケットと PR の状態を `source_ref` から引く取り込みを足し、観測があるときだけ `done` を silent に付ける。
3. **入口を増やす**。チケット、議事録、Teams。議事録は生成で決定事項を出し、タスク候補か否かは閉じた集合で決める。
4. **MCP 側にも枝を適用する**。いま `engine::plan_view` / `check_view` / `close_view` は枝を通らないので、MCP クライアントからは既知の節でも質問が出る。
5. **帯を測る**。20件を測ったあとにだけ、未知の節の自動適用（第一判断を Jev に渡す）へ進む。
